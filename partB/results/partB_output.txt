B1 (a) KV-CACHE BYTES PER TOKEN
==========================================================================================
  bytes/token = 2 (K and V) x layers x kv_heads x head_dim x dtype_bytes
              = 2 x 28 x 8 x 128 x 2
              = 114,688 bytes = 112 KiB per token
  NOTE: kv_heads = 8, not the 24 query heads. This model uses GQA; using 24
        would overstate KV by exactly 3x and is the classic error here.

  per 4096-token sequence = 114,688 x 4096 = 469,762,048 B = 0.4375 GiB

B3 THE MISREAD COLUMN: reported_tok_s
==========================================================================================
  Hypothesis: reported_tok_s counts PROMPT + GENERATED tokens, i.e. all tokens the
  GPU touched, not the tokens the user received. Test on all 13 rows:
   bs  plen glen  reported  (p+g)n/wall   gn/wall  ratio
    1   512  256      70.2         70.2      23.4   3.00
    2   512  256     132.3        132.3      44.1   3.00
    4   512  256     261.0        261.0      87.0   3.00
    8   512  256     495.4        495.5     165.2   3.00
   16   512  256     883.2        883.4     294.5   3.00
   32   512  256    1489.6       1489.5     496.5   3.00
   64   512  256    2267.3       2267.2     755.7   3.00
    4  3584  512     565.4        565.4      70.7   8.00
    8  3584  512     902.6        902.7     112.8   8.00
   16  3584  512    1311.4       1311.5     163.9   8.00
   24  3584  512    1607.4       1607.3     200.9   8.00
   32  3584  512    1384.0       1383.9     173.0   8.00
   48  3584  512    1298.5       1298.5     162.3   8.00

  All rows match (p+g)*n/wall: True
  The inflation factor is (prompt+gen)/gen -- a CONSTANT PER PROMPT LENGTH:
      short rows 512+256 -> 768/256 = 3.00x
      long  rows 3584+512 -> 4096/512 = 8.00x
  So the long-prompt rows are inflated 2.67x MORE than the short ones. The report
  compared an 8x-inflated number (1311.4) against a 3x-inflated number (883.2) and
  read the difference as a hardware property. Both of its Section 2 conclusions
  come from this one column.

  HONEST GOODPUT OF THE BATCH-24 LONG-PROMPT ROW -- two independent derivations:
    (1) from wall clock: gen_len x num_requests / wall_clock_s
        = 512 x 24 / 61.16 = 12288/61.16 = 200.9 output tok/s
    (2) from reported_tok_s: strip the known 8.00x prefill inflation
        = 1607.4 x (512 / 4096) = 1607.4/8 = 200.9 output tok/s
    (3) sanity check from itl_ms_p50 = 96.07 ms (steady-state decode ceiling)
        1000/96.07 = 10.41 tok/s per sequence x 25 resident = 260.2 tok/s
        Higher than 200.9 because wall clock also pays prefill and drain;
        it bounds goodput from above, and 200.9 < 260.2. Consistent.

  'LONGER PROMPTS GIVE BETTER THROUGHPUT' -- at matched batch 16:
    short prompts: reported 883.2 -> goodput 294.5 output tok/s
    long  prompts: reported 1311.4 -> goodput 163.9 output tok/s
    Long prompts are 44% WORSE, not better. The conclusion is inverted.

  'BATCH 48 SHOULD GIVE ~3200 tok/s':
    measured at batch 48: reported 1298.5, goodput 162.3
    the projection overstates even the inflated counter by 2.46x, and real goodput by 19.7x
    (it also mis-sources its own anchor: best reported_tok_s in the log is 2267.3 at batch 64 short, not '~1600')

B2 THE THROUGHPUT ANOMALY IN THE 3584 SWEEP
==========================================================================================
   bs   goodput  linear ideal    eff   wall_s  ttft_ms  itl_ms  preempt    kv
    4      70.7          70.7   100%    28.98    483.2   51.33        0  0.16
    8     112.8         141.3    80%    36.30    519.0   62.26        0  0.31
   16     163.9         282.7    58%    49.97    498.3   77.20        0  0.62
   24     200.9         424.0    47%    61.16    500.5   96.07        0  0.93
   32     173.0         565.4    31%    94.71    636.9  101.79        7  0.97
   48     162.3         848.0    19%   151.41    955.4  100.00       23  0.97

  ANOMALY: goodput rises monotonically to batch 24 (200.9 tok/s) and then FALLS --
  173.0 at batch 32 and 162.3 at batch 48. Adding 100% more concurrency makes the
  system 19% SLOWER in absolute terms. Naive 'throughput scales with batch' predicts
  424 -> 848 tok/s; we observe 201 -> 162.

  MECHANISM (specific rows and columns):
   - kv_cache_util goes 0.93 (bs24) -> 0.97 (bs32) -> 0.97 (bs48): the KV pool
     saturates. B1 says it holds ~25 full-length sequences; 32 and 48 do not fit.
   - preempted_seqs goes 0 -> 7 -> 23, and 32-7 = 48-23 = 25 resident in both cases.
     The scheduler admits more than it can hold and evicts the excess.
   - A preempted sequence loses its KV and must re-prefill 3584 tokens when it is
     rescheduled. That prefill work is done twice or more and produces no extra
     output tokens -- pure waste. It shows up as ttft_ms_p50 483->500->637->955
     (queueing + repeated prefill) while itl_ms_p50 flattens at ~100 ms: the decode
     step is not getting slower, the requests are simply not resident.
   - wall_clock_s confirms: 61.16 -> 94.71 -> 151.41 s. Batch 48 takes 2.48x the
     wall time of batch 24 to do 2.00x the requests.
   - This is memory-capacity thrash, not compute saturation. At 200 output tok/s
     the model is nowhere near the L4's 121 TFLOPS or 300 GB/s roofline.

  PROPOSED CHANGE: set max_num_seqs = 24 (from the default 256).
    The 48-request workload then runs as two clean waves of 24 instead of one
    thrashing wave of 48.
    PREDICTED wall clock: 2 x 61.16 = 122.32 s
    MEASURED at batch 48:                  151.41 s
    predicted improvement: 19.2% lower wall clock
    predicted goodput: 48 x 512 / 122.32 = 200.9 tok/s  vs 162.3 measured  (+24%)
    predicted preempted_seqs: 0 (from 23)
    Falsifiable: if goodput does not land near 201 tok/s, preemption was not the
    dominant cost and the mechanism above is wrong.
