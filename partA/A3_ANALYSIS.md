# A3 — Corrected analysis and the denominator question

Generated by `python run_a3.py`; committed output in `results/a3_table.txt`.

## Tokenizers

| spec | what | status here |
|---|---|---|
| `gpt2` | the tokenizer REPORT_v0 actually measured | ✅ real, offline, sha256-pinned |
| `bytes` | UTF-8 bytes — the theoretical floor for any byte-level BPE | ✅ real |
| `spm:vendor/spm_multi.model` | locally trained BPE, byte_fallback, coverage 1.0 | ✅ real but **contaminated** |
| `hf:xlm-roberta-base` | 250k multilingual vocab, Indic-aware | ⏳ needs network |
| `hf:ai4bharat/IndicBERTv2-MLM-only` | Indic-specialised | ⏳ needs network |

`bytes` is not a deployment candidate. It is in the table as a reference line:
any byte-level BPE that has learned nothing about a script converges to it, so
the gap between a tokenizer and `bytes` *is* its vocabulary coverage for that
script.

The SentencePiece model is trained on the same text it is measured on. Its
absolute numbers are an optimistic bound and I do not quote them as estimates of
anything. It is admissible for exactly one claim — that a vocabulary covering
these scripts does not hit byte fallback — and for nothing quantitative.

## Results (smoke corpus, 12 parallel sentences — pipeline demonstration)

> These are **not** eval numbers. Run `make corpus && make a3-full` for those.

**GPT-2**, ratios vs English:

| lang | tok/word | tok/codepoint | tok/grapheme | tok/byte | **tok/sentence** |
|---|---|---|---|---|---|
| hin | 6.05 | 6.74 | 10.16 | 2.53 | **5.60** |
| kan | 15.50 | 11.27 | 18.12 | 4.13 | **11.11** |
| tam | 18.38 | 11.63 | 18.51 | 4.21 | **13.44** |
| tel | 15.40 | 11.46 | 20.87 | 4.21 | **11.26** |

The five denominators disagree with each other by up to **3.5×** on the same
text with the same tokenizer. Picking a denominator is therefore not a
presentational detail; it *is* the analysis. REPORT_v0 picked two, got two
different answers (5.89 and 7.0), and called that agreement.

Absolute token counts, GPT-2 vs raw bytes:

| lang | GPT-2 | UTF-8 bytes | GPT-2's saving |
|---|---|---|---|
| eng | 84 | 354 | 76.3% |
| hin | 470 | 782 | 39.9% |
| kan | 933 | 951 | 1.9% |
| tam | 1129 | 1129 | **0.0% — identical** |
| tel | 946 | 946 | **0.0% — identical** |

For Tamil and Telugu, GPT-2 *is* a UTF-8 byte tokenizer, exactly. This is the
cleanest possible refutation of REPORT_v0's "property of the script" claim.

## Which single number should drive routing and cost

> **Tokens per parallel sentence**, on a truly parallel corpus, for the
> tokenizer you would actually deploy — reported as a ratio against English.

### Why

The denominator has to hold constant **the thing the customer is buying**. A user
does not send you words, characters or bytes. They send a request that means
something, and you bill them for the tokens it takes to represent that meaning.
So the denominator must hold *meaning* constant, and the only construct that does
that across languages is a parallel sentence.

Each alternative fails on a specific, measurable ground:

- **tok/word** — a word is not a cross-linguistically constant unit. Measured on
  the parallel corpus, the same 12 sentences take 5.58 words in English but 4.00
  in Kannada, because Kannada is agglutinative. So tok/word divides a large
  numerator by a small denominator and reports the product of two independent
  effects as one. It systematically over-penalises agglutinative languages. It is
  also the metric v0 used, and it is why Kannada looks 15.5× worse per word but
  11.1× worse per sentence.
- **tok/codepoint** — confounded by script density. Devanagari packs a syllable
  into fewer codepoints than Latin packs it into letters, and Indic combining
  marks make the codepoint count depend on encoding choices rather than on
  content.
- **tok/grapheme** — better than codepoints, because a grapheme cluster is closer
  to what a reader perceives as a character. Still orthography, not meaning, and
  it produces the *widest* spread in the table (up to 20.9×), which should make
  anyone suspicious of it as a cost proxy.
- **tok/byte** — the fairest *encoding* measure and the right diagnostic for
  vocabulary coverage (this is what proves the byte-fallback finding). But it is
  meaning-unfair: it hands a structural advantage to any language that UTF-8
  encodes in one byte. Nobody is billed per byte.
- **tok/sentence** — holds content constant by construction. This is the number
  that converts directly into money: multiply by your price per token and you
  have cost per request, in a form that survives translation.

### The caveat that comes with it

"Sentence" is a proxy for "one user request", and it is a decent one only because
FLORES lines are single sentences of comparable content. In production the honest
version of this metric is **tokens per completed user turn**, measured on real
traffic. The corpus version is the offline stand-in, and A4's production monitor
is what checks whether the stand-in held.

## Reproduce

make a3            # offline: gpt2 + bytes + spm on the smoke corpus
